# まちカルテ（仮）設計書

Nov 2, 2026 · @Rito

## 目的とスコープ

PLATEAUの建物属性のうち、調査が及んでいない建物を自動で絞り込み、推定した属性を人が確認して、自治体がそのまま使える更新候補リストとして出力する。

対象は新宿区の1地区。絞り込みから更新候補の出力までを1本通すことに集中する。

### 設計を決めた3つの制約

いずれも実データで確かめた事実で、ここから設計が決まっている。

| 制約 | 事実 | 設計への帰結 |
| --- | --- | --- |
| 名寄せが不可能 | 不明群4,968棟に住所がない。不動産IDは0件。地番ポリゴンは新宿区の92%が任意座標系 | 自動で紐づけず、候補を出して人が地図で確定する |
| 用途推定は6割が頭打ち | 近傍かつ高さ±3mで56.8%。最頻値は43.1% | 推定は候補として出し、信頼度を添える。確定は人 |
| 階数は高さからかなり当たる | 高さ÷3.8mで62.3%、±1階許容で92.1% | 階数は自動で埋め、人は確認するだけ |

### 作るもの

1. 調査リストの抽出（自動）
2. 属性の推定と、根拠・信頼度の提示（Claude）
3. 地図上での確認と確定（人）
4. 建物ID付きの更新候補リストの出力（自動）

### 作らないもの

- スマホアプリ化、市民参加の仕組み
- 複数自治体への横展開（長岡市・すさみ町は課題の裏づけに数字で触れるだけ）
- 自治体システムへの書き込み
- 公式データの直接書き換え（更新候補の出力までが責任範囲）

### 優先するもの

デモで見せたいものが2つ決まっている。**57,780棟が4,982棟に減る瞬間**と、**1棟あたりの処理時間**。どちらもUIがないと見せられないので、推定の精度向上よりUIの立ち上げを優先する。

## 全体構成

要は、すべての外部データを建物IDに寄せてから扱う。寄せられないものは、人が地図で確定するまで候補のまま置いておく。

### 技術選定

| 層 | 選ぶもの | 理由 |
| --- | --- | --- |
| データ処理 | Python + DuckDB | CityGMLの解析と、OvertureのGeoParquetをそのまま読める。空間演算もDuckDBの拡張で足りる |
| 地図 | MapLibre GL JS | オープンソースでトークンが不要。Google Mapsは規約上使えず、Mapboxはトークンが要る |
| API | FastAPI | GeoJSONと候補値を返すだけなので軽いもので足りる |
| 推定 | Claude API（構造化JSON） | 画像判定、根拠の言語化、判断不能の自己申告 |
| 確定の保存 | DuckDB（同一ファイル） | 1週間なのでDBを分けない。処理時間の記録もここ |

背景地図について。MapLibreのスタイルには、国土地理院のタイルか、OpenStreetMap由来のオープンなタイルを使う。どちらも出典表示で使える。

## データモデル

`uro:buildingID`（例：`13104-bldg-2923`）を単一キーにする。外部情報はすべて「建物ID → 候補値、信頼度、根拠」の形で付与し、元の属性は上書きしない。

### buildings（基礎テーブル）

CityGMLから1回だけ作る。

| 列 | 内容 |
| --- | --- |
| `building_id` | 主キー。`13104-bldg-2923` |
| `city_code` | 市区町村コード。13104で絞る |
| `geom` | LOD0外形。EPSG:6677 |
| `height_m` | `measuredHeight`。-9999はNULLに正規化 |
| `storeys_above` | 9999はNULLに正規化 |
| `usage` | 461はNULLに正規化（「不明」という値ではなく欠損として扱う） |
| `survey_year` | 0001はNULLに正規化 |
| `roof_edge_area` | -9999はNULLに正規化 |
| `creation_date` | 版の判別に使う |
| `lod_type` | テクスチャの有無の判定 |
| `is_target` | 調査対象フラグ。後述の条件で立てる |

**センチネル値の正規化が最初の関門。** 9999、-9999、0001、461、1011を素通しすると、平均も件数も壊れる。読み込み時に一括でNULLにし、`is_target`で区別する。

### candidates（推定結果）

1つの建物に複数行入る。属性ごと、ソースごとに1行。

| 列 | 内容 |
| --- | --- |
| `building_id` | buildingsへの参照 |
| `attribute` | `usage` / `storeys` / `year_built` / `detailed_usage` |
| `value` | 推定値。建築年は区間で持つので`value_min`と`value_max`も |
| `confidence` | 0.0〜1.0 |
| `source` | `poi` / `osm_building` / `image` / `neighbor` / `height` / `version_diff`（`osm_building` は 2026-11-03 追記。OSM の building タグを POI とは別ソースとして評価するため） |
| `reasoning` | Claudeが返した根拠の文章 |
| `evidence_ids` | 根拠になったPOIや画像への参照 |

**「判断不能」も1行として記録する。** `value`をNULL、`confidence`を0にして、`reasoning`に理由を入れる。黙って行が無いのと、判断できないと答えたのは別物として扱う。

### confirmations（人の確定）

| 列 | 内容 |
| --- | --- |
| `building_id`, `attribute` | 何を確定したか |
| `confirmed_value` | 人が確定した値 |
| `accepted_candidate` | 候補をそのまま採ったか、修正したか |
| `opened_at`, `confirmed_at` | **処理時間の計測用。ここが「1棟あたり数秒」の出どころ** |
| `operator_note` | 自由記述 |

### evidence（根拠の実体）

POI、画像、旧版との差分など、推定の根拠になったものを保存する。デモで「なぜそう推定したか」を見せるときに引く。

### 座標系

| 用途 | 座標系 |
| --- | --- |
| 幾何演算（内包判定、IoU、距離） | EPSG:6677（平面直角第9系、JGD2011） |
| 地図表示、GeoJSON出力 | EPSG:4326 |

CityGMLはEPSG:6697（緯度経度＋標高）で入っているので、読み込み時に6677へ変換する。距離や面積をメートルで扱えないと、5〜10mの近傍判定が書けない。

## 第1段：絞り込み（自動）

ここが完全自動で、デモの山場。PLATEAUのデータだけで動く。

### 不明群の判定

次のどれか1つで判定できる。実データで、6つすべてが同じ4,982棟を指すことを確認済み。

```sql
-- 判定条件（どれか1つで足りる。確実を期すなら AND でつなぐ）
usage = '461'
AND detailed_usage = '0'
AND storeys_above = 9999
AND survey_year = '0001'
```

実装では`usage = '461'`を主条件にし、残りは整合性チェックとして件数が一致するかを検証する。ずれたら前提が崩れているので、そこで止める。

### 新しく現れた建物の検出

2つの方法がある。**精度が違うので、両方やる。**

| 方法 | 内容 | 精度 |
| --- | --- | --- |
| `creationDate` | 2026-03-13なら新版で作成 | 弱い。5,796棟が該当するが、うち4,009棟は2021年の属性を持っている。形状の作り直しも含まれる |
| **版間の建物ID差分** | 2023年度版と2025年度版の建物IDを突き合わせ、新版にしかないものを抽出 | 強い。これが本命 |

版間差分には2023年度版のダウンロードが必要。Day 1〜2で実施する。建物IDが版をまたいで安定しているかは要検証で、安定していなければ外形のIoU照合に切り替える。

### 優先度の付け方

4,982棟すべてを同列に扱うと、担当者は何から見ればいいか分からない。次の順に並べる。

1. **高さが大きい棟**（影響が大きく、画像も得やすい）
2. **新しく現れた棟**（版間差分で検出したもの）
3. **外形面積が大きい棟**
4. **テクスチャまたはMapillary画像がある棟**（確認しやすい）

実データでの分布は、高さ10m以上が895棟、20m以上が196棟、45m以上が21棟、100m以上が6棟。**高さ20m以上の196棟なら、デモの範囲として現実的**。

### 出力

`is_target`フラグと優先度スコアをbuildingsに書き込み、地図用のGeoJSONを吐く。これが「調査リスト」になる。

## 第2段：推定（Claude）

属性ごとに手法が違う。**精度の実測値に応じて、どこまで自動で埋めるかを変える。**

| 属性 | 主な手法 | 実測ベースライン | 扱い |
| --- | --- | --- | --- |
| 階数 | 高さ ÷ 用途別階高 | 62.3%（±1階で92.1%） | 自動で埋め、人は確認のみ |
| 用途 | POI結合 ＋ 画像判定 | 56.8%（近傍＋高さ） | 候補を出し、人が確定 |
| 建築年 | 版間差分 ＋ 年代別写真 | — | 点推定せず、区間で出す |
| 詳細用途 | 用途が決まってから | — | 用途の確定後に候補提示 |

### POI結合（用途推定の本命）

先行研究では、周辺ラベルのベースラインが56.0%で、こちらの実測56.8%とほぼ同じ。**外観の上乗せは数ポイントから十数ポイントにとどまる一方、POIの直接結合は効く**という結果が出ている。だからここを主軸にする。

1. Overture PlacesとOSM POIを、まず厳密にポリゴン内包で判定する
2. 外れたPOIは5〜10m以内の最近傍ポリゴンに割り当て、距離に応じて信頼度を下げる
3. 1棟に複数POIがある場合は、カテゴリ分布を特徴量にする（雑居ビルの判定に効く）

**高層棟では地上のPOIが1階部分しか表さない**点に注意。住友不動産新宿ファーストタワーのようなオフィスと住宅の複合では、POIだけでは用途が決まらない。こういう棟こそ人に回す。

### 階数推定

高さ÷3.8の一律ではなく、**用途別の階高を既知棟から学習して使う**。実測値は住宅3.80m、共同住宅3.70m、業務施設3.96m、文教厚生施設4.47m。

ただし高層棟では外れる。35階建ての2棟で、高さ÷3.8の推定はA棟38階、B棟31階と、どちらもずれた。**高さが45mを超える棟は、推定値に「高層のため誤差が大きい」と注記を付ける。**

### 画像判定

画像の供給源は3段構え。カバレッジの穴を埋める。

| 順 | 供給源 | 対象 | 注意 |
| --- | --- | --- | --- |
| 1 | Mapillary | 街路から見える棟 | カバレッジ要実測。視錐台レイキャストで建物に割り当てる |
| 2 | 東京都区部オルソ 0.2m | 屋根の判定 | 簡易オルソなので高層は倒れ込む。高さに応じてバッファ |
| 3 | PLATEAU LOD2テクスチャ | 補助のみ | 不明群の16%しかなく、投影ずれで屋上や隣接建物が混入する |

**Mapillaryの建物への割り当て**が技術的な肝。位置に`computed_geometry`、向きに`computed_compass_angle`、画角は`camera_parameters`の焦点距離から求める。カメラ点から2Dのレイを放射し、最初に当たった外形エッジを「見えている建物」とする。距離8〜40m、入射角60°以内に絞る。

### Claudeに渡すもの、返させるもの

画像だけでなく、**PLATEAUから分かる事実を一緒に渡す**。外観だけで判断させない。

**入力**

- 建物の画像（1〜3枚、供給源を明記）
- 高さ、外形面積、用途地域、周辺建物の用途分布
- 内包または近傍のPOIのカテゴリと名称
- 用途コードの選択肢（Building\_usage.xmlの18コード）

**出力（JSON固定）**

```json
{
  "usage": { "value": "412", "confidence": 0.82,
    "reasoning": "バルコニーが全階に並び、住戸の区画が規則的。POIに不動産管理会社" },
  "storeys": { "value": null, "confidence": 0.0,
    "reasoning": "画像に屋上と道路が混入しており、階数を数えられない" },
  "unresolvable": ["storeys"]
}
```

**「判断不能」を明示的に返させる**のが要点。`unresolvable`に入った属性は、信頼度に関係なく人に回す。デモでは、この挙動をあえて1件見せる。

### 建築年

点推定しない。**区間と根拠だけを出す。**

- 2023年度版になく2025年度版にある → 「2022〜2024年の間に新築」
- 地理院の年代別オルソで外形をクリップし、建物が現れた年代を判定 → より古い区間も推定できる

57,780棟すべてで`yearOfConstruction`が空なので、区間でも入れば新しく生まれる価値になる。

## 第3段：人が確定する画面

**ここを最優先で立ち上げる。** デモで見せたい2つが、どちらもこの画面に依存している。

### 地図画面

- 新宿区の建物をMapLibreで表示。調査対象の4,982棟を色づける
- **絞り込みの前後を切り替えられるようにする。** 全57,780棟が表示された状態から、対象だけに絞られる瞬間を見せるため。デモの山場なので、アニメーションを付ける価値がある
- 優先度順のリストをサイドに置き、クリックで地図が飛ぶ
- 西新宿にズームした初期表示を用意しておく（デモの開始位置）

### 確認画面

1棟を選ぶと開く。1画面で完結させ、スクロールさせない。

| 要素 | 内容 |
| --- | --- |
| 建物の画像 | 供給源を明記（Mapillary / オルソ / LOD2テクスチャ） |
| 現在の属性 | 「不明」と表示。PLATEAUの実際の値も併記 |
| 推定候補 | 属性ごとに、値・信頼度・根拠の文章 |
| 選択肢 | 用途コードの選択肢を並べ、推定値を既定で選択済みにする |
| 操作 | 「そのまま確定」と「修正して確定」の2ボタン |
| 判断不能の表示 | Claudeが`unresolvable`を返した属性は、警告色で理由を出す |

**そのまま確定が1クリックで済む**ことが、処理時間を短くする鍵。推定が当たっていれば、人は読んで押すだけになる。

### 処理時間の計測

後付けできないので、確認画面を作るときに同時に入れる。

- 建物を開いた時刻を`opened_at`に記録
- 確定した時刻を`confirmed_at`に記録
- 画面に「処理済み N棟 / 合計 M分 / 1棟あたり S秒」を常時表示
- 「そのまま確定」と「修正して確定」で時間を分けて集計する

**デモでは、連続して数棟を処理して見せる。** 画面の数字が増えていくのが、そのまま「人の作業がどれだけ軽いか」の証拠になる。

### 画面に出さないもの

- 推定の内部スコアや特徴量（担当者には不要）
- 信頼度の生の数値だけ（「高・中・低」と根拠の文章で示す）

信頼度を数字で出すと、根拠を読まずに数字で判断してしまう。**根拠の文章を主役にして、数字は補助にする。**

## 第4段：更新候補の出力

公式データは書き換えない。**自治体が確認したうえで反映できる差分**として出す。

### 形式

2つ出す。用途が違う。

| 形式 | 用途 |
| --- | --- |
| CSV | 担当者が表計算で開き、突き合わせる |
| GeoJSON | GISに取り込み、地図上で確認する |

### 列定義（CSV）

| 列 | 内容 |
| --- | --- |
| `building_id` | `13104-bldg-2923` |
| `attribute` | `usage` / `storeys_above` / `year_built` |
| `current_value` | PLATEAUの現在値。`461`や`9999`をそのまま出す |
| `current_label` | `不明` |
| `proposed_value` | 確定した値。`401` |
| `proposed_label` | `業務施設` |
| `source` | `poi` / `osm_building` / `neighbor` / `image` / `height` / `version_diff`（`neighbor`・`osm_building` は 2026-11-03 追記。近傍推定を確定・出力できるようにし、OSM building タグを別ソースとして扱うため） |
| `confidence` | 推定時の信頼度 |
| `reasoning` | 推定の根拠（Claudeが返した文章） |
| `confirmed_by` | 確定した人 |
| `confirmed_via` | 確定の経路。`desk`（机上の確認画面）/ `onsite`（スマホの現地調査）。`source` が推定の出どころを表すのに対し、こちらは誰がどこで確定したかを表す（2026-11-05 追記） |
| `confirmed_at` | 確定日時 |
| `evidence_url` | 根拠になった画像やPOIへの参照 |

**`current_value`と`proposed_value`を並べるのが要点。** 何を何に変えるのかが1行で分かり、自治体側で差分を機械的に当てられる。

### 建築年の扱い

区間で出すので列が違う。`proposed_value`には`2022-2024`のように範囲を入れ、`value_min`と`value_max`を別列で持つ。点推定を求められても出さない。

### 出力しないもの

- 人が確定していない推定値（candidatesに留める）
- 判断不能と返った属性

**確定したものだけが出力に乗る。** ここを曖昧にすると、公式データとして使えないものが混ざる。

### 帰属表示

出力ファイルのヘッダーか、添付のREADMEに、使ったデータ源のライセンス表記を入れる。画面にも帰属表示をまとめたページを用意する。

## 計測と検証

**既知の52,161棟が、そのまま正解データになる。** 属性を隠して推定させ、正解と突き合わせれば、精度を実測できる。審査の「深さと実行」はここで取る。

### 正解率の測り方

1. 既知棟から検証用に無作為抽出する（ホールドアウト）
2. 属性を伏せて推定パイプラインにかける
3. 正解と突き合わせ、属性ごとに正解率を出す

**ソースを1つずつ足したときの上積みを可視化する。** これが審査で効く。

| 段階 | 用途の正解率 |
| --- | --- |
| 最頻値のみ | 43.1%（実測済み） |
| ＋ 近傍の用途 | 49.5%（実測済み） |
| ＋ 高さ±3m | 56.8%（実測済み） |
| ＋ POI結合 | **Day 1で判定** |
| ＋ 画像判定 | Day 2〜4で判定 |

### Day 1の判断基準

POI結合で56.8%を超えるかどうか。**超えなければ用途推定の主軸を画像に移すか、「用途は候補提示にとどめ、階数と建築年で勝負する」に切り替える。** Day 1のうちに結論を出す。

どちらに転んでも成果物は成立する。絞り込みと差分出力という骨格は、用途推定の精度に依存していない。

### 処理時間の測り方

`confirmations`の`opened_at`と`confirmed_at`の差を集計する。

- そのまま確定した場合と、修正した場合で分ける
- 中央値を使う（1件の中断で平均が壊れるため）
- デモでは連続処理の実測値を見せる

### デモで出す数字

| 数字 | 出どころ |
| --- | --- |
| 訪問が必要な棟数の削減率 91.4% | 57,780棟 → 4,982棟。PLATEAUのデータのみ |
| 推定の正解率 | 既知棟でのホールドアウト検証 |
| 1棟あたりの処理時間 | confirmationsの実測 |

### 数字の言い方の注意

「1棟N秒 × 4,982棟」という掛け算は出せるが、**全棟を同じ速度で処理できるわけではない**ので避ける。「確認が必要な棟に絞れば、現実的な時間で回せる」程度にとどめる。

「半年の踏査」との対比は効くが、出どころを言えるようにしておく。都市計画基礎調査の実施方法として説明できる状態にする。

## 実装順序

**UIを前に、推定を後ろに。** デモで見せたい2つがUIに依存しているので、推定の精度向上より画面の立ち上げを優先する。精度が伸びなくても、見せたいものは守れる。

| 日 | やること | 終わった時点で動くもの |
| --- | --- | --- |

| Day 1–2 | **地図UIを立ち上げる。** 全棟表示から対象だけに絞る切り替え、クリックで属性表示 | 絞り込みの瞬間が見せられる |

## 未決定事項と分岐点

### Day 1に判断すること

**POI結合で用途の正解率が56.8%を超えるか。** これが最大の分岐点。

| 結果 | 取る道 |
| --- | --- |
| 超えた | POI結合を主軸にする。画像は補助 |
| 超えない | 画像を主軸に切り替える。または「用途は候補提示にとどめ、階数と建築年で勝負する」 |

どちらでも成果物は成立する。絞り込みと差分出力という骨格は、用途推定の精度に依存していない。

### 検証が必要なこと

| 項目 | いつ | 失敗したときの代替 |
| --- | --- | --- |
| 建物IDが版をまたいで安定しているか | Day 1–2 | 外形のIoU照合に切り替える |
| Mapillaryの新宿区でのカバレッジ | Day 2 | 東京都のオルソとLOD2テクスチャで補完 |
| 視錐台レイキャストで建物を正しく特定できるか | Day 2–3 | 距離と入射角の条件を厳しくし、対象棟を絞る |
| Overture Buildingsの属性充足率 | Day 1 | OSMのタグのみに頼る |

### まだ決めていないこと

- **リポジトリのライセンス。** ODbLとCC BY-SAの継承義務と整合させる。キックオフ前に決める
- 帰属表示の具体的な文面
- デモ動画の構成（ガイドにGoogleドライブの資料がある）
- 対象とする地区の範囲。西新宿を中心に、何棟を扱うか

### 意図的に決めていないこと

- 用途コードの細分化をどこまでやるか。詳細用途まで踏み込むかは、用途の精度が出てから判断する
- 複数人での確認やレビューの仕組み。1週間では作らない

### 前提が崩れたら止める点

実装中に、次が成り立たないと分かったら設計を見直す。

- 不明群の4,982棟が、1つのフラグで判定できなくなる（版が変わった場合など）
- 建物IDが外部データとの唯一のキーとして機能しない
- Claudeが「判断不能」を安定して返さない（根拠なく断定してしまう場合）

最後の1つは、プロンプトの設計で対処する。Day 3の画像判定を作るときに、既知棟で挙動を確認する。
